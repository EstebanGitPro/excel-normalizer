Cómo usar EGM (Elephant-Goldfish Model)

Guía práctica para usar el plugin google/elephant-goldfish-model con Claude Code en este proyecto: qué es, cómo se instala, el flujo de trabajo y los comandos.

1. La idea en una frase

Diseñás con un elefante y revisás con un pez dorado.

El elefante "nunca olvida": conoce tu proyecto, la charla y las decisiones anteriores. Con todo eso escribe el diseño. El pez dorado "no recuerda nada": lee solo el documento y el código que el documento cita. Si el documento no se entiende sin la charla previa, el pez dorado lo va a notar. Ese es el truco: detecta los supuestos que diste por obvios y nunca escribiste.

🐘 Elefante

Conoce el proyecto, los requisitos y las decisiones previas. Explora el problema y redacta la especificación.

🐟 Pez dorado

Lee solo el documento y el código que referencia, sin la conversación previa. Encuentra supuestos ocultos, requisitos confusos y riesgos.

🧑 Vos

Conocés los objetivos reales. Resolvés los trade-offs, aprobás el diseño y decidís qué se construye.

¿Por qué funciona? Cuando un mismo agente diseña y revisa, revisa con los mismos sesgos con los que diseñó. Un revisor con contexto limpio se parece más a lo que le va a pasar al próximo programador (o a vos dentro de 6 meses) que abra el documento sin saber nada.

2. Instalación en Claude Code

# 1. Agregar el marketplace del plugin
claude plugin marketplace add google/elephant-goldfish-model

# 2. Instalar el plugin completo
claude plugin install egm@egm

Después abrí una sesión nueva de Claude Code para que se carguen los comandos.

  • Instalá el plugin completo, no solo la carpeta skills/: las skills leen en tiempo de ejecución las personas de agents/ y los estándares de resources/.
  • Las revisiones necesitan subagentes con contexto limpio. Claude Code los tiene (herramienta Agent). Si un entorno no los tiene, EGM corta la revisión en vez de fingirla.
  • Los comandos llevan el prefijo /egm:. Por ejemplo: /egm:egm-review.
  • Las skills tienen disable-model-invocation: true: solo se activan cuando vos escribís el comando. Claude no las dispara solo.

3. El flujo principal, paso a paso

egm-brainstorm→egm-draft→egm-review→egm-resolve→revisión humana→implementar→egm-drift-report

  1. Explorar la idea

    /egm:egm-brainstorm Agregar <la funcionalidad nueva> al normalizador.

    El agente te hace preguntas abiertas en varios turnos hasta que el problema y sus límites queden claros. No lanza a los peces dorados hasta que vos confirmes que está listo. Después varios revisores atacan la idea en paralelo, cada uno desde un ángulo distinto. Resultado: concepts_brief.md.

  2. Redactar la especificación

    /egm:egm-draft

    Convierte el brief en design_draft.md, sección por sección, y frena después de cada una para que des tu opinión en el chat.

  3. Revisar con peces dorados

    /egm:egm-review design_draft.md

    Cinco etapas, cada una con un revisor de contexto limpio:

    1. Zoom out inicial: ¿el diseño resuelve el problema correcto?
    2. Comprensión: ¿se entiende sin la charla previa?
    3. Crítica de diseño: ¿cuáles son los puntos débiles y los casos borde?
    4. Zoom out intermedio: ¿sigue teniendo sentido en el conjunto?
    5. Listo para implementar: ¿alcanza el plan para construirlo?

    Va a dar mucho feedback, a propósito. Quedate con lo relevante e ignorá el resto.

  4. Resolver los hallazgos

    /egm:egm-resolve

    Recorren juntos cada hallazgo y deciden qué cambiar en el documento.

  5. Revisión humana

    Mandá el diseño en un PR a otra persona. EGM no reemplaza a un humano, lo complementa.

  6. Implementar

    Pedile al agente que construya siguiendo el documento. Si se equivoca un poco, corregís puntualmente. Si se va muy lejos, el problema está en el documento: lo actualizás y repetís.

  7. Controlar la deriva (una vez por semana)

    /egm:egm-drift-report docs/designs/

    Compara cada documento de diseño con el código actual y te dice dónde se separaron. Vos elegís si actualizar el documento o el código.

4. Todas las skills

No hace falta seguir el flujo completo. Usá la que resuelva tu cuello de botella del momento.

ComandoPara quéProduce
/egm:egm-brainstormPoner a prueba una idea a medio cocinar.concepts_brief.md
/egm:egm-draftConvertir un brief o unas notas en un documento de diseño.design_draft.md
/egm:egm-review <doc>Revisar un diseño en 5 etapas con peces dorados.Informe de revisión
/egm:egm-resolveTrabajar los hallazgos de la revisión y acordar cambios.Documento actualizado
/egm:egm-review-loopCorrer un grupo de revisores a medida, también para documentos que no son de software.Informe
/egm:egm-bootstrap <ruta>Generar los README de un código que ya existe, de abajo hacia arriba.README.md por carpeta
/egm:egm-drift-report <carpeta>Comparar los documentos con el código actual.Reporte de deriva

5. Cómo encaja en este proyecto (excel-normalizer)

Estructura recomendada

excel-normalizer/
└── docs/
    ├── COMO-FUNCIONA.md              ← ya existe
    ├── explicacion-*.html            ← guías de aprendizaje
    └── designs/                      ← NUEVO: diseños aprobados de EGM
        ├── SITEMAP.md                ← índice de los diseños
        └── <funcionalidad>.md       ← una especificación por funcionalidad

Un buen primer uso, sin escribir nada nuevo

Para probar EGM con algo que ya existe, pasale a un pez dorado la guía actual:

/egm:egm-review docs/COMO-FUNCIONA.md

Si el pez dorado no entiende algo de esa guía sin tu contexto, es una señal de qué le falta.

Para la funcionalidad nueva

  1. /egm:egm-brainstorm con la idea, en una frase.
  2. Respondé las preguntas con calma. Es la etapa más valiosa.
  3. /egm:egm-draft y aprobá sección por sección.
  4. /egm:egm-review sobre el borrador.
  5. Guardá el diseño aprobado en docs/designs/ y recién ahí se implementa.

6. Cosas a tener en cuenta

TemaQué saber
Costo y tiempoBrainstorm y review lanzan varios subagentes, así que gastan más tokens y tardan más que una charla normal. No lo uses para un bug de una línea: "usá la herramienta correcta para el trabajo", dice la propia guía.
TonoLos revisores tienen la orden de no adular: critican primero, buscan contraargumentos y no dicen "excelente idea". Es intencional.
Tu otro flujo (SDD)Ya tenés instaladas skills de sdd-* (explore, propose, spec, design…) que hacen algo parecido. Conviene elegir uno por funcionalidad para no mezclar artefactos (concepts_brief.md y design_draft.md contra propuestas y specs de SDD). La diferencia fuerte de EGM es la revisión con contexto limpio en 5 etapas.
Archivos, no chatEGM escribe los resultados en archivos y te pasa la ruta. No espera que leas un plan largo en el chat.
No reemplaza testsUna revisión de diseño no reemplaza los tests ni el criterio humano.
